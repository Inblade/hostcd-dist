Engineering validation

Seven failure scenarios on four real hosts

hostcd is not a slideware control plane. Its recovery paths are exercised by a live failure-injection drill on real Linux hosts — not simulate mode. This is what that drill is, and what it isn't.

The drill runs against one control plane and four real Ubuntu 24.04 hosts (Gcore, Frankfurt-2). The agents apply real packages, files and services — nothing is faked in memory. Each scenario injects a concrete failure and asserts that the fleet recovers to the state declared in Git.

Results

#ScenarioWhat was injected → expected recoveryResult
S1Baseline convergesFresh fleet → all four hosts online, app base Synced/HealthyPASS
S2Control-plane crash / restartKill the control plane → hosts hold their config; on restart the apps reload and the fleet reconvergesPASS
S3Corrupted state → snapshot recoveryCorrupt state.json → the server recovers applications from its .bak snapshotPASS
S4Agent crash + drift self-healKill the agent and hand-edit /etc/motd → on agent restart the managed content is restoredPASS
S5Network partition toleratedPartition a host → it goes offline on the control plane but keeps its config, then reconnects and re-Syncs after the healPASS
S6Host reboot auto-recoversReboot a host → systemd restarts the agent; the host comes back online and SyncedPASS
S7Load: 50 extra managed filesAdd 50 managed files → the fleet re-Syncs in ~3s with the files present on every hostPASS

Result: 7 passed, 0 failed. The drill also covers load and rolling/HA upgrades; the scripts and committed reports live in the repository.

What this is — and what it isn't

Be clear-eyed about the claim. This is a point-in-time chaos run against a handful of hosts, authored and run by the maintainer. It is real evidence that the recovery paths work, on real machines, not in a mock. It is not a continuously-green CI gate, a large-scale soak test, or third-party validation. Those come with a paying pilot, not a demo.
